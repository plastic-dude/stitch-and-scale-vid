It invites designers to inspect one current artifact header, draft/review/test/release badge, version/date marker, change-note panel, release-state label, or accessible artifact metadata surface if proof is supplied; it does not promise that Stitch & Scale provides any of those behaviors.

## Research decision

GOV.UK publishing guidance distinguishes drafting from publishing and supports change notes for updates. ONS guidance says essential information should be available in an accessible alternative and recommends clear descriptive file names, while Yarnpond and prior test-knit research show that tester-facing copies and updated versions need explicit workflow context. The craft-business and publishing contracts require stable identifiers, status, history, readable exports, localization, and human review. None of this proves Stitch & Scale has artifact state labels, version history, change notes, or automatic distribution.

## Concept and dramatic engine

| Engine element | Director decision |
|---|---|
| Subject | A pattern artifact is about to be handed to a tester or reader. |
| Desire | To know exactly what the artifact is, who it is for, and what changed before work begins. |
| Obstacle | Draft, review, test, and release copies can look visually similar while carrying different expectations. |
| Stakes | A tester may work from the wrong copy or a reader may treat a review artifact as final; no actual product outcome is claimed. |
| Change | The fictional header names `STATE / VERSION / AUDIENCE / CHANGE NOTE`. |
| Contradiction | A descriptive filename helps, but a filename alone cannot prove currentness. |
| Escalation | Unlabeled page → state ambiguity → audience/version fields → change note → deliberate handoff. |
| Final image | An artifact card with `TEST COPY — REVIEW BEFORE USE`; no release badge. |

## Difference from nearest prior angle

The nearest prior angle is `change-notice`, which focuses on disclosing that a test or requirement changed. `artifact-status` changes the pain to **not knowing which copy/state a person is holding before they begin**. The hook changes to **“The file is not ready until its state is readable.”** The visual metaphor changes from a changed-version card to an artifact header **`DRAFT / REVIEW / TEST COPY / RELEASE`** with audience and change-note fields. The proof surface changes from a change notice to a current artifact header, state badge, version/date marker, change-note panel, release-state label, or accessible artifact metadata surface. The emotional turn changes from understanding a change to knowing what one is holding. The final line changes to **“Name the copy before you hand it over.”**

It is distinct from `publication-readiness` because it is not general quality readiness; from `reader-handoff` because it is artifact identity before the handoff rather than reading support; from `change-notice` because it is not the changed requirement itself; from `source-note` because it is state and audience identity rather than provenance; from `context-lock` because it is not active record context; and from imported `release-gate-roster` because it is artifact identity, not completion accountability or a gate roster. Neither imported concept is reopened, renamed, overwritten, or approved.
