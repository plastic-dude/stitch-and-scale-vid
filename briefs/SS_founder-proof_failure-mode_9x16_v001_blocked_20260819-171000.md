## Concept and distinctness

A status can look acceptable while the way it could fail remains unnamed. The nearest prior angle is `evidence-type`, which identifies what an evidence form supports and does not support. `failure-mode` changes the pain to a result or workflow status appearing acceptable while its possible failure path, initiating event, effect, detection, or mitigation is invisible. The hook becomes “A pass is not a failure mode.” The visual metaphor changes from paired question/evidence cards to a scenario path branching from initiating event to failure mode, effect, detection, trigger, mitigation, owner, and status. The proof surface is `SCENARIO / INITIATING EVENT / FAILURE MODE / EFFECT / DETECTION / LIKELIHOOD / CONSEQUENCE / MITIGATION / TRIGGER / OWNER / STATUS`. The emotional turn is from respecting evidence limits to making possible failure visible before trust. The final line is “Name how it can fail before you trust the pass.” It does not recreate evidence type, evidence coverage, provenance chain, uncertainty context, assumption register, acceptance criteria, false completion, release roster, or a human release checklist.
