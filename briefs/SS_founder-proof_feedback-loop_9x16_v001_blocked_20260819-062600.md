## Research decision

A practitioner guide from A Bee In The Bonnet distinguishes technical editing from test knitting: technical editors work in the abstract and may not knit the item, while test knitters offer varied experience and language perspectives. It also cautions that test knitters can catch major errors while missing smaller ones and should not be treated as a complete substitute for technical editing. Current Craft Industry Alliance search results were reviewed for feedback and pattern-platform context, but no specific test-knit workflow article was verified in this run, so no detailed market claim was used.

The research changed the concept from a generic tester story to **response accountability**. The film must not claim that testers approved, issues are resolved, the pattern is correct, or one round is enough.

## Campaign assumption

No active human brief was present in the checked repository state. This run assumes founding-tester recruitment remains the working objective through the free demo and early-access cohort. The film invites designers to inspect one verified feedback or issue/response surface; it does not promise a complete feedback system, release gate, issue tracker, or tester outcome.

## Dramatic engine

| Element | Director decision |
|---|---|
| Subject | A test-knitter observation lands on a pattern draft and waits for a response. |
| Desire | To know what was observed, what changed, what must be rechecked, and what remains unresolved. |
| Obstacle | A note can disappear in messages or be mistaken for resolution merely because someone read it. |
| Stakes | Unanswered or untracked feedback can be repeated, forgotten, or prematurely treated as approval. |
| Change | The viewer moves from “feedback received” to “feedback has a visible response state and recheck path.” |
| Contradiction | Accountability does not mean every note is accepted; it means the disposition is explicit. |
| Escalation | Observation appears → read receipt tempts closure → response note → recheck card → unresolved state remains visible → current proof or blocker. |
| Final image | Four cards align: `OBSERVED / RESPONDED / RECHECK / UNRESOLVED`, with no green release badge. |

## Difference from prior concepts

The nearest prior angle is `false-completion`, which is a broader imported blocked concept about premature completion across human gates. `feedback-loop` changes the pain to **a specific tester observation disappearing or being mistaken for approval when no response path is visible**; the hook to **“A note is not resolved because someone read it.”**; the visual metaphor from a generic completion state to a feedback card moving through `OBSERVED / RESPONDED / RECHECK / UNRESOLVED`; the proof surface from a generic human gate to a current feedback, issue/response, or test-knit record surface; the emotional turn from fear of false closure to accountable respect for tester labor; and the final line to **“Show me what happened after the note.”**

It is distinct from `false-completion` and `release-gate-roster` because it is not a general or rostered release decision; from `correction-trace` because it is not a version-history or correction-line story; from `sample-chain` because it is not physical custody; and from `equivalent-meaning`, `material-notes`, `gauge-reality`, `reader-handoff`, `chart-parity`, `readability-under-load`, `measurement-moment`, `decision-ledger`, `recovery-proof`, `permission-line`, `event-window`, `evidence-over-output`, `inherited-thread`, `offline-continuity`, and `locale-drift` because the conflict is observation-to-response accountability. It does not reopen, overwrite, rename, or consume the imported reservations.

## Treatment, visual grammar, and production bible

Open on an original feedback card carrying a fictional identifier such as `NOTE A-01`, permanently labeled `ILLUSTRATIVE — NOT PRODUCT UI`. The card contains an abstract observation, not a real correction or private tester message. It moves through four separate paper states: `OBSERVED`, `RESPONDED`, `RECHECK`, `UNRESOLVED`. None is green, approved, or release-ready.

The product insert is optional and blocked until a current, versioned, non-private proof capture verifies exact feedback, issue, response, unresolved, or test-knit record labels. If absent, retain `FEEDBACK PROOF REQUIRED — NOT PRODUCT UI`. Test knitting, technical editing, physical print review, chart readability, schematic scale, and release decisions remain distinct. David may appear only with authorization and must be described only as a developer whose late mother knitted; he is not a knitter, knitwear designer, pattern designer, or technical editor. Use one narrator family. Captions must not cover note ID, state cards, proof, hands, or CTA. Review caption-on and caption-free cuts.
