## Research decision

W3C explains that sequential focus must preserve meaning and operability, and that pointer targets need a minimum size or spacing under the stated exceptions.[300] [301] Maker and accessibility sources describe the extra work involved in progress tracking, clear hierarchy, explicit language, written equivalents, large-print variants, and user testing.[302] [303] [304] [305] YouTube, TikTok, and Instagram provide current publishing constraints that support a short, vertical, caption-reviewed master.[306] [307] [308] [309] Stitch & Scale’s internal contracts require mobile reachability, interruption/recovery testing, and separate technical, print, chart, schematic, and test-knit evidence.[310] [311] [312] [313] None of this proves current product behavior.

## Concept and dramatic engine

| Engine element | Director decision |
|---|---|
| Subject | One critical interaction path from project context to a saved or recoverable result. |
| Desire | To complete the next safe maker action without losing context or guessing what received focus. |
| Obstacle | A polished screen can be visible while focus order, focus visibility, target spacing, validation, save, or recovery remain unknown. |
| Stakes | A designer may enter or act on the wrong context; no user outcome or product defect is claimed. |
| Change | The fictional path changes from a static “accessible” badge to explicit task, context, sequence, feedback, and recovery evidence. |
| Contradiction | A control can be visible and still not be reachable in a meaningful sequence. |
| Escalation | Screen → task context → focus path → validation/save → recovery → proof or blocker. |
| Final image | `FOCUS PATH VISIBLE — PRODUCT PROOF REQUIRED`. |

## Difference from nearest prior angle

The nearest prior angle is `spoken-index`, which focuses on semantic fields, ordering, and equivalent text for spoken instructions. `focus-path` changes the pain to **whether an interactive task can be reached and completed in a logical pointer/keyboard sequence**. The hook changes to **“Visible is not reachable.”** The visual metaphor changes from spoken row/round instruction order to a path of focus states through a maker task. The proof surface changes from spoken-instruction/equivalent-text fields to a current interaction-context surface showing task, context, focus order, focus visibility, target size/spacing, validation, save, and recovery evidence. The emotional turn changes from semantic confidence in an audio instruction to agency when the action path is explicit. The final line changes to **“Show the path before you call the action accessible.”**

It is distinct from `hands-busy` because it is about interaction sequence, not physical hand occupancy; from `equivalent-meaning` because it is about operating a control path, not content parity across access modes; from `caption-clearance` because it is not video-caption layout; from `readability-under-load` because it is not visual density; from `offline-continuity` and `recovery-proof` because it does not claim network or restoration behavior; from `export-portability` because it does not concern transported files; and from `submission-state` because it does not concern editorial or rights lifecycle. It does not reopen or reuse `false-completion` or `release-gate-roster`.

## Treatment and production bible

Open on an original abstract card marked `ILLUSTRATIVE — NOT PRODUCT UI`. A hand or cursor approaches a visible control, but the card refuses to call it complete. The path is then typed as `TASK / PROJECT / SIZE / UNIT / INPUT / FOCUS ORDER / FOCUS VISIBLE / TARGET SIZE / VALIDATION RESULT / SAVE STATE / RECOVERY PATH`. The path pauses at `PROOF REQUIRED` rather than becoming a fabricated UI.

A current Stitch & Scale interaction-context capture may replace the fictional card only if a current, approved, non-private proof registry entry verifies exact labels, focus behavior, pointer/touch state, product version/date, and rights to show the capture. No screenshot may be treated as proof of keyboard or target-size behavior without recorded interaction evidence. If proof is absent, retain the blocker card and disclaimer.

Use one narrator family. David may appear only with authorization and remains described as a developer whose late mother knitted; he is not a knitter, knitwear designer, pattern designer, or technical editor. Captions must not cover hands, cursors, controls, focus indicators, error states, numbers, proof, logos, menus, or CTA. Review caption-on and caption-free versions. Generated text remains illustrative and cannot substitute for current product labels or interaction evidence.

## Caption map and audio plan

Use one narrator family with close, dry narration. Sound motif: a soft pointer click on `VISIBLE`, a restrained keyboard tap on `FOCUS ORDER`, a small confirmation tone only on the illustrative `VALIDATION RESULT` card, and silence before `PROOF REQUIRED`. No accessibility-certification swell, disability-emotion cue, or “success” chime that implies a product outcome. Check for voice drift, doubled words, overlaps, accent changes, room-tone jumps, and inconsistent mic distance.

Captions are narration-verbatim, sentence by sentence, inside a declared safe zone that never covers controls, focus indicators, cursors, hands, error/save/recovery states, proof, or CTA. Keep one action-path family on screen at a time for mobile reading. Retain caption-on and caption-free review masters. Automatic captions are not accepted as final. No audio description, screen-reader, or accessibility claim is made for the video itself without separate review.

## Locations, arrangements, and visual grammar

Use one quiet tabletop and one neutral interaction surface with diffuse light, no private data, and no brand or publisher marks. Arrange `TASK/PROJECT/SIZE/UNIT → INPUT/FOCUS → VALIDATION/SAVE/RECOVERY` as a vertical sequence. Use close-ups for one field family at a time. Keep all generated text visibly fictional and never style it as current UI. If a real product capture arrives, show one interaction state at a time with evidence timestamp and version/date in the manifest.
