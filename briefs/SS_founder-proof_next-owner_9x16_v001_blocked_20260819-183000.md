## Research decision

Craft Yarn Council distinguishes how a designer contacts a recipient, submits to one company or magazine at a time, waits for an approximate response, and later discusses fee/contract after acceptance.[343] W3C distinguishes status messages from focus and explains that status updates can be announced without changing context.[344] Atlassian’s RACI guidance separates responsible, accountable, consulted, and informed roles.[345] Stitch & Scale’s internal contracts require visible operational follow-up, source/date, stable IDs, context, and recovery boundaries.[350] Current platform and caption guidance supports a short vertical master with human-reviewed captions.[346] [347] [348] [349] None of this proves current Stitch & Scale assignment behavior.

## Concept and dramatic engine

| Engine element | Director decision |
|---|---|
| Subject | One handoff or status change that needs a named next action. |
| Desire | To know what happens next, who may act, and what is only an expectation. |
| Obstacle | A status can record what happened while leaving the next actor, recipient, or response window implicit. |
| Stakes | A designer may wait, chase, or assume ownership without evidence; no real delay or outcome is claimed. |
| Change | The fictional card changes from a status badge to a bounded next-action record with owner/role, response window, source/date, and notes. |
| Contradiction | A status can be accurate and still leave the work motionless. |
| Escalation | Current state → next action → owner/role → recipient → response window → source/date → proof or blocker. |
| Final image | `NEXT OWNER VISIBLE — PRODUCT PROOF REQUIRED`. |

## Difference from nearest prior angle

The nearest prior angle is `submission-state`, which distinguishes a sent project from acceptance, contract, publication, or rights transfer. `next-owner` changes the pain to **a status that names what happened but not who acts next**. The hook changes to **“A status without an owner is a waiting room.”** The visual metaphor changes from a submission lifecycle to a handoff card with a single next-action arrow and explicit owner/role, recipient, response window, source, and notes. The proof surface changes from submission state to current next-action/owner context. The emotional turn changes from separating status outcomes to restoring agency through a bounded handoff without guaranteeing a response. The final line changes to **“Name who acts next before you call it moving.”**

It is distinct from `feedback-loop` because it is not a routing/history loop; from `work-scope` because it is not tester labor; from `support-boundary` because it is not the scope of help; from `permission-line` because it is not access authority; from `reader-handoff` because it is not reader continuation; from `artifact-status` because it is not copy identity; from `event-window` and `deadline-truth` because time is supporting context, not the primary pain; from `change-notice` because it is not a diff; from `payment-state` because it is not a money lifecycle; and from `submission-state` because it is not an editorial/contract/publication state. It does not reopen or reuse `false-completion` or `release-gate-roster`.
