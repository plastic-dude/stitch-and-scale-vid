## Research decision

GitHub review guidance ties feedback to changed files and review outcomes such as comment, approve, or request changes.[359] A current knitting technical-editing workflow describes comments as inputs the designer uses to correct and clarify the pattern, with service scope needing confirmation.[360] CYC frames pattern production as a process involving designer, editor, final editing/printing, and project-specific requirements.[361] Current platform and caption guidance supports a short vertical master with human-reviewed captions.[362] [363] [364] [365] Internal contracts keep project/size/unit context, technical editing, test knitting, chart readability, schematic scale, print review, export identity, and issue reproducibility separate.[366] None of this proves current Stitch & Scale review anchoring.

## Concept and dramatic engine

| Engine element | Director decision |
|---|---|
| Subject | One review comment attached to a specific pattern revision and location. |
| Desire | To know exactly which artifact, size, section, and review round the comment concerns. |
| Obstacle | A comment can float across revisions, sizes, or rounds when its anchor is implicit. |
| Stakes | A designer may correct the wrong copy or assume a comment applies everywhere; no real defect or outcome is claimed. |
| Change | The fictional comment gains artifact/version, size/unit, section/location, round, severity, status, source/date, owner, and next action. |
| Contradiction | A helpful comment can still become unsafe when its context is lost. |
| Escalation | Comment → artifact/version → size/unit → section/location → round → severity/status → response → proof or blocker. |
| Final image | `REVIEW ANCHOR VISIBLE — PRODUCT PROOF REQUIRED`. |

## Difference from nearest prior angle

The nearest prior angle is `correction-trace`, which links a post-release correction to the copy a reader uses. `review-anchor` changes the pain to **a review comment losing its exact revision, size, section, or round context before correction**. The hook changes to **“A comment without a version is a loose thread.”** The visual metaphor changes from a correction trail to a comment pin attached to a fictional artifact/version/size/section card with review-round and response fields. The proof surface changes from post-release errata linkage to current review-context anchoring. The emotional turn changes from reader correction safety to reviewer/designer clarity before a revision. The final line changes to **“Anchor the comment before you correct the pattern.”**

It is distinct from `change-notice` because it is not a diff communication; from `feedback-loop` because it is not feedback routing; from `inherited-thread` because it is not conversation carryover; from `repro-note` because it is not issue reproducibility alone; from `artifact-status` because it is not copy state; from `context-lock` because it is not active context selection; from `quote-permission` because it is not public reuse rights; from `next-owner` because it is not next-action ownership; and from `submission-state` because it is not editorial/contract/publication state. It does not reopen or reuse `false-completion` or `release-gate-roster`.

## Treatment and production bible

Open on an original abstract card marked `ILLUSTRATIVE — NOT PRODUCT UI`: `COMMENT: “Check this increase.”` A loose pin floats beside three fictional cards: `V1 / SIZE M / BODY`, `V2 / SIZE M / SLEEVE`, and `V2 / SIZE XL / BODY`. The pin becomes anchored only when the record adds `VERSION OR ARTIFACT`, `SIZE`, `UNIT`, `SECTION OR LOCATION`, and `REVIEW ROUND`. A second line adds `SEVERITY / STATUS / SOURCE / DATE / OWNER / NEXT ACTION`. The narrator refuses to claim automatic mapping across sizes or versions. A final card reads `REVIEW ANCHOR VISIBLE — PRODUCT PROOF REQUIRED`.

A current Stitch & Scale review-context capture may replace fictional cards only if a current, approved, non-private proof registry entry verifies exact anchor labels, product version/date, stale-thread behavior, review-round semantics, and rights to show the capture. A screenshot cannot prove that a comment applies to the current artifact or every size; interaction/data evidence is required. If proof is absent, retain the blocker card and disclaimer.

Use one narrator family. David may appear only with authorization and remains described as a developer whose late mother knitted; he is not a knitter, knitwear designer, pattern designer, or technical editor. Captions must not cover comment text, version, size, unit, section, review round, status, hands, menus, logos, or CTA. Review caption-on and caption-free versions. Generated text remains illustrative and cannot substitute for current product labels or review evidence.
