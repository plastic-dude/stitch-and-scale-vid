## Fresh research question

After a pattern file is reviewed, what evidence proves that the released artifact is the **same reviewed file** rather than merely another export that opens in a reader?

This question is narrower than `export-portability`, which concerns survival across readers, devices, formats, metadata, units, charts, and print. It is also distinct from `backup-state` and `archival-state`, which concern recoverability and future retrieval; from `capture-freshness`, which concerns whether a capture is current; and from `publication-boundary`, which concerns whether a release should proceed. Pass 224 focuses on **identity continuity between the reviewed artifact and the released artifact**.

## Research synthesis

A file that opens is not necessarily the file that was reviewed. A hash or signature can help identify or authenticate a byte sequence, but it does not prove the pattern’s math, grading, instructions, chart readability, schematic scale, physical print behavior, or test-knit behavior. The craft guidance reinforces that a submission is a package of distinct files and human checks, not one finished-looking artifact.

The film should dramatize the handoff from a fictional `REVIEWED_ARTIFACT` card to a fictional `RELEASED_FILE` card. The cards should remain separate until `FILE_ID`, `VERSION`, `HASH`, `CAPTURED_AT`, `SOURCE_COMMIT_OR_RECORD`, and `REVIEW_STATUS` are visible. The final state must remain `IDENTITY MATCH: UNVERIFIED` because no current product surface is proven. This provides a materially different story from export portability: it does not ask whether a file survived a new reader or device, but whether the released file is the same artifact that received review.

The seasonal Knitty context is useful as publication preparation but must not become urgency or affiliation. The category research does not support attacking Adobe or GitHub; it supports a bounded observation that document or build systems can preserve identity/provenance evidence, while Stitch & Scale’s own behavior remains unverified. Rights and privacy are central: do not use a real pattern, PDF, signature, hash, commit, customer export, or publication submission.

## Decision

Select the new angle **`export-identity-state`**. It is materially different from the nearest recent angle `cost-allocation-state` because it concerns reviewed-versus-released artifact identity, not shared-expense attribution. It is also distinct from `export-portability`, `backup-state`, `archival-state`, `capture-freshness`, `publication-boundary`, `preview-state`, `version-lock`, `chart-parity`, `paper-proof`, and the imported blocked concepts.

The proposed hook is: **“A file that opens is not proof it is the file you reviewed.”** The visual metaphor is two fictional pattern cards, `REVIEWED_ARTIFACT` and `RELEASED_FILE`, separated by a gate that only opens when identity fields match. The final line is: **“Match the file before you call it released.”** These are bounded creative lines, not claims about current product UI.

The proof surface, if supplied, must distinguish: `EXPORT E-001 / DESIGN_ID / SOURCE_RECORD_OR_COMMIT / REVIEWED_ARTIFACT_ID / RELEASED_FILE_ID / FILENAME / VERSION / HASH_ALGORITHM / HASH / HASH_CAPTURED_AT / LOCALE / UNIT / REVIEWER / REVIEWED_AT / REVIEW_STATUS / RELEASE_STATUS / DERIVED_FROM`. A matching identity signal is not technical approval; the human evidence gates remain separate.
